# Qabyl / Freedom Pay — подготовка к подключению

Дата: 14 сентября 2026. Изменения локальные: сайт и production Supabase не обновлялись.

## Граница готовности

Подготовлены публичные страницы, кабинет, разовый hosted checkout, проверка подписей,
транзакционное проведение оплаты, резервирование покупок, сверка зависших успешных платежей,
безопасная основа автопополнения и отдельная граница маршрутизации предоплат.

**Нельзя объявлять весь эквайринг production-ready только после ввода ключей.**
Сохранение/замена карты, безакцептные списания, автоматическое продление, отправка возвратов
и Partner API требуют согласованного контракта Freedom Pay, реализации соответствующего
адаптера и банковских acceptance-тестов. Эти возможности сейчас отключены и на сервере,
и в интерфейсе. Никаких успешных mock-платежей в пользовательском потоке нет.

## 3. Миграция

`supabase/migrations/20260913151910_payment_safety.sql` создана, **не применена к production**.
Локально выполнялась дважды в изолированной PGlite-базе для проверки повторного применения.

Расширяет подписки настройками порога/размера пакета и отметками согласия; счета —
состоянием отправки, адресом checkout и суммой возврата. Новое автопополнение по умолчанию выключено.
Старый `auto_topup=true` без новой отметки согласия не разрешает списание.

Добавляет две server-only таблицы с RLS и без прав anon/authenticated:
`payment_accounts` (будущие аккаунты салонов, только ссылки на хранилище секретов) и
`payment_webhook_events` (минимальный журнал без полных запросов, номеров карт и токенов).

RPC доступны только service_role:

- `billing_reserve_invoice`: блокировка строки подписки, запрет второй незавершённой покупки
  того же вида и повторной покупки сразу после успешной; защита оплаченного периода.
- `billing_settle_invoice`: счёт, начисление, подписка и уведомление в одной транзакции.
- `billing_receive_event`: событие и его эффекты в одной транзакции, semantic dedup.
- `billing_reserve_topup`: согласие, баланс, цена из тарифа, cooldown и резервирование под одним lock.
- `billing_claim_dispatch`: однократное разрешение отправки; отключение до claim отменяет покупку.
  После claim операция считается отправляемой: отключение не гарантирует её остановку.

Перед применением сделать backup и прогнать полную цепочку миграций на staging Supabase.
PGlite-тесты используют минимальную совместимую схему, а не заменяют тест полного проекта.

## 4. Переменные окружения

Только backend:

| Переменная | Назначение |
|---|---|
| `PAYMENTS_ENABLED` | `1` включает разовую оплату после применения миграции и проверки условий; иначе новые платежи выключены; callbacks и сверка продолжают работать |
| `FREEDOMPAY_MERCHANT_ID` | Тестовый идентификатор мерчанта Qabyl |
| `FREEDOMPAY_SECRET_KEY` | Секрет подписи в серверном secret storage |
| `FREEDOMPAY_TESTING` | По умолчанию тестовый режим; только явное `0` выбирает боевой |
| `FREEDOMPAY_API_BASE` | Необязательно; разрешён только `https://api.freedompay.kg` |
| `PUBLIC_APP_URL` | HTTPS-origin приложения; production `https://qabyl.com` |
| `SUPABASE_SERVICE_ROLE_KEY` | Уже используемый серверный доступ к базе |
| `SUPABASE_URL` / `VITE_SUPABASE_URL` | Уже используемый адрес Supabase |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Публичный ключ для каталога через RLS, не секрет |

Старый `FREEDOMPAY_RECURRING_SCRIPT` больше не используется: нельзя включить непроверенный
endpoint переменной окружения. Не добавлять платёжные секреты с префиксом VITE_.
Production credentials не использовались и в `.env` не записывались.

## 5. Что получить от Freedom Pay

1. Sandbox merchant ID / secret key, тестовые карты и сценарии отказа, подтверждение KGS
   и одноэтапного списания с клирингом. Точное имя мерчанта в выписке клиента.
2. Активированные возможности hosted checkout, безопасного сохранения/замены/удаления карты,
   recurring или card-token MIT; официальное описание выбранного контракта и callback примеры.
3. Условия mandate/согласия, 3DS/SCA, срок действия сохранённого способа, last4/brand/expiry,
   идентификатор клиента в рамках мерчанта. Изоляция клиента должна учитывать salon_id.
4. Идемпотентность **каждого этапа** MIT, правила повторов, unknown timeout и сверки,
   terminal failure/cancel statuses, доставка/повторы Result URL.
5. Формат возвратов (включая частичные), события, API чеков/квитанций и требования фискализации.
6. Partner API: модель юридического договора, onboarding/KYC салона, account/terminal routing,
   где находятся секреты, кто получает деньги и отвечает за refund/chargeback.
7. Подтвердить callback: `https://qabyl.com/api/public/billing/freedompay`, POST form-urlencoded,
   подпись с именем скрипта `freedompay`; return URLs `/admin/billing?payment=success|failed`.
   Return URL не является источником истины.

## 8. После получения параметров

Сначала staging-миграции и тестовые ключи, затем end-to-end разовая оплата/подписанный callback/
сверка. После согласования карточного контракта реализовать недоступные методы PaymentProvider,
hosted сохранение/замену и verified callback метода оплаты, UI согласия на продление и его
сохранение. Подключить scheduler recurring только при согласии и capability, а автопополнение —
к уже готовым reserve/claim операциям. Нельзя просто сменить capability на true без этого.

Возвраты сейчас поддержаны как транзакционная модель учёта подтверждённой суммы;
отправка возврата в банк, внешний refund callback и изменение оплаченных прав не включены.
Не выдавать ручной перевод или отметку интерфейса за банковское подтверждение.
Partner API подключать отдельно: сервис сейчас намеренно не создаёт предоплаты на Qabyl merchant.

## 9. Риски и практические ограничения

Устранены: предположительный PayBox recurring endpoint; доверие unsigned API response;
read-then-write начисление; race автодокупки; произвольная сумма/NaN; сохранение исходной строки
PAN вместо last4; ложный success toast; автоматическое закрытие неизвестного исхода по времени;
управление оплатой ролью master через server functions.

Остаются до сертификации: форматы terminal statuses/refund, fiscal receipts, замена и отзыв карты,
правила согласия и retention. У неизвестной операции нет автоматического повторного дебета:
сверка восстанавливает подтверждённый success; неподтверждённые/ошибочные статусы требуют
операторского разбора. Это сознательный приоритет защиты от двойного списания.

При ошибках Supabase блок оплаты выдаёт сообщение об обновлении; выложить сервер и миграцию
согласованно. Проверить действующий cron и его лимит исполнения: сверка ограничена 20 счетами
за цикл, каждый запрос имеет timeout. Большому потоку потребуется отдельный worker/очередь.
Ранее накопленные дубли/некорректные маски требуют отдельного read-only аудита данных перед запуском.

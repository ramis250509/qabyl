## Критическая цепочка

### 1. Поднять тестовый полигон *(10 минут)*

Старый проект в Токио (`khykprcdojksqvuqyajd`) идеально подходит: 0 записей
клиентов, полная схема, и он всё равно под снос. Docker не нужен.

```bash
npx supabase link --project-ref khykprcdojksqvuqyajd
```

```bash
npx supabase db push
```

Спросит пароль от базы Токио — он в вашем менеджере паролей. Накатит всю
цепочку миграций, включая три новые.

**Зачем.** Сейчас три миграции не проверены нигде. Одна из них меняет
`create_appointment` — функцию, через которую проходит каждая запись клиента.
Применять такое на прод вслепую нельзя.

**Скажите мне, когда пройдёт** — я прогоню там поведенческие тесты
(`supabase/tests/booking_integrity.sql`) и скажу, что именно сломается, если
что-то сломается.

### 2. Применить миграции на прод *(5 минут, после моего «ок»)*

Только после пункта 1. Три миграции:

- `20260813120000_booking_integrity_fixes.sql` — закрывает обход предоплаты,
  прямой INSERT мимо RPC, запись в выходной мастера
- `20260813130000_level1_booking_ops.sql` — упреждение, аудит-лог, статус доставки
- `20260813140000_public_rate_limits.sql` — ограничение частоты

Делать в нерабочее время салонов. Пока не применены, **три критические дыры
живы в проде**: предоплату можно подтвердить не заплатив, календарь можно забить
через прямой запрос, а салон — превратить в ретранслятор WhatsApp-спама за его
же счёт.

### 3. Передеплоить edge-функцию *(2 минуты)*

Cloudflare подхватит Worker сам при пуше в `main`, но edge-функции Supabase
деплоятся отдельно. Я менял `send-whatsapp`:

```bash
npx supabase functions deploy send-whatsapp
```

Без этого статус доставки подтверждений писаться не будет.

### 4. Включить вебхук статуса в Green-API *(5 минут)*

Личный кабинет Green-API → настройки инстанса → включить **`outgoingMessageStatus`**.

Именно этот вебхук приносит `noAccount` — ответ на ваш исходный вопрос «почему
запись создаётся с номером, которого нет в WhatsApp». Без него плашка в
календаре будет застревать на «отправлено», не доходя до «не доставлено».

Касается салонов на Green-API (сейчас это Lashes Nurzhan).

### 5. Влить ветку и выкатить *(5 минут)*

```bash
git push -u origin audit/level-1-booking-integrity
```

Дальше PR в `main` — Cloudflare выкатит в прод автоматически. Проверьте, что
CI зелёный: он теперь гоняется на каждый push.

## После выката

### 6. Добавить секрет для CI *(3 минуты)*

GitHub → Settings → Secrets and variables → Actions → New repository secret.
Имя `SUPABASE_DB_URL`, значение — строка подключения из Supabase → Settings →
Database → Connection string (URI).

После этого CI начнёт проверять инварианты схемы на каждый push: гранты,
RLS-политики, ограничения. Именно они ловят самые дорогие баги за секунды.

**Только после пункта 2** — иначе job будет красным по делу, но бесполезно.

### 7. Настроить упреждение записи *(2 минуты на салон)*

Админка → Ассистент → «Закрывать онлайн-запись перед визитом». По умолчанию 0
(выключено). Разумное значение для салона красоты — 60–120 минут.

### 8. Разобраться с 33 алертами *(30 минут)*

За 30 дней алерт «Ассистент не отвечает клиентам» сработал 33 раза, последний —
11 августа. Это либо реальные простои ассистента, о которых вы не знали, либо
слишком чувствительный порог. И то и другое стоит выяснить: если простои
реальные, вы теряете клиентов молча.

Я могу посмотреть по логам, если скажете.

## Отдельным вечером: ротация ключей

Не входит в цепочку выше и **не должна делаться в тот же вечер, что миграции**.
Оба действия трогают прод, и если после них что-то отвалится, вы не поймёте,
что именно виновато. Разнесите на разные дни.

Порядок с предупреждениями — [KEY-ROTATION.md](KEY-ROTATION.md). Два места, где
легко положить прод:

- `CRON_SECRET` живёт одновременно в vault и в секретах edge-функций. Между
  обновлениями рассылки не работают — делать в нерабочее время салонов.
- `VAPID_PRIVATE_KEY` **не трогать**: смена инвалидирует все push-подписки, всем
  админам и мастерам придётся заново разрешать уведомления. В переезде он не
  участвовал и утечь не мог.

**Срочность ниже, чем у пунктов 1–2.** Три дыры в проде эксплуатируемы прямо
сейчас; ротация — страховка от утечки, которой могло и не быть. Но и
откладывать на месяц не стоит: старые ключи ходили между машиной, дашбордами и
логами во время переезда.

Пароль от базы Токио для пункта 1 менять не нужно — проект всё равно под снос.

## Решения, которые нужны от вас (не работа, а выбор)

### Форматирование репозитория

34 000 замечаний линтера, почти все — переводы строк Windows против Unix. Чинится
одной командой (`bun format` + `.gitattributes`), но даёт коммит, трогающий почти
каждый файл. Пока не сделано: такой коммит хоронит историю изменений и его нельзя
осмысленно проверить. Нужно ваше «да» и отдельный момент, когда нет незакрытых
веток.

### Что дальше по уровням

Отложены сознательно, потому что требуют новых непроверенных миграций поверх уже
имеющихся трёх:

- **Единый движок расписания** (уровень 2, п. 6). Сейчас «работает ли салон в
  этот день» решается дважды: в SQL и в TypeScript. Каждое расхождение — это
  ассистент, говорящий клиенту «у нас выходной», когда салон работает.
- **Рабочий день и перерыв одновременно** (уровень 2, п. 7). Сейчас в базе
  нельзя выразить «работаю 10–18, перерыв 13–14»: строка либо рабочий день,
  либо перерыв.

Оба делаются сразу после пункта 1 — когда появится где проверять.

Из уровня 3 не начато: онбординг салона без вашего участия, платёжная
интеграция вместо чеков MBANK, страница клиента с историей визитов,
мультиязычность до конца. Это месяцы, а не вечер.

# Qabyl → self-service SaaS. Архитектура, разрывы, план

Дата: 2026-09-09. Повод: Meta одобрила `whatsapp_business_messaging` и
`whatsapp_business_management` (App Review, 07.09.2026).

Документ отвечает на три вопроса: что есть сейчас, чего не хватает, и в каком порядке это
закрывать. Всё, что здесь названо разрывом, проверено по коду и по проду, а не предположено.

---

## 1. Что есть сейчас

### 1.1 Тенантность

Тенант — строка `salons`. Привязка человека к тенанту — `user_roles (user_id, role, salon_id,
branch_id)`. Роли: `super_admin` (вся платформа), `salon_admin` (один салон), `manager`
(операционка без настроек), `master` (свой календарь).

Изоляция держится на RLS и на функциях `has_salon_access` / `has_salon_ops_access` /
`has_branch_access`. Серверные функции (`createServerFn`) дополнительно зовут
`has_salon_access` руками, потому что ходят через `supabaseAdmin` в обход RLS.

`salon_secrets` — отдельная таблица, у роли `authenticated` нет `SELECT`. Браузер видит её
только через серверные функции. Решение правильное.

### 1.2 WhatsApp: транспорт

Пайплайн один, транспортов три (`src/lib/wa-transport.server.ts`, интерфейс `WaTransport`):

| Транспорт | Файл                     | Зачем появился                       | Салонов в проде            |
| --------- | ------------------------ | ------------------------------------ | -------------------------- |
| `cloud`   | `wa-cloud.server.ts`     | основной, официальный Meta Cloud API | 2 (оба тестовые/нерабочие) |
| `make`    | `wa-transport.server.ts` | обход Standard Access через Make     | **0**                      |
| `gupshup` | `wa-gupshup.server.ts`   | обход через BSP                      | 1 (тестовый салон)         |

Разделение транспорта и пайплайна сделано аккуратно: агент, блокировка диалога, слив
накопившихся сообщений, дедуп — общие для всех каналов, включая Instagram.

### 1.3 WhatsApp: вебхуки

Два маршрута:

- `/api/public/wacloud` — общий вебхук приложения Qabyl. Маршрутизация тенанта по
  `metadata.phone_number_id`. Подпись — `X-Hub-Signature-256` общим `META_APP_SECRET`.
  Коллизия «один номер у двух салонов» ловится (`limit(2)`, отказ + запись в `error_logs` обоим).
- `/api/public/wacloud/$salonId` — для салона со СВОИМ приложением Meta, подпись его app secret.

Оба сходятся в `processWaCloudPayload`. Дедуп входящих — уникальный индекс на
`wa_messages.green_api_message_id`. Ответ всегда 200, чтобы Meta не отписала приложение.

Это спроектировано верно и переписывать не нужно.

### 1.4 Embedded Signup

Реализован и рабочий по сути:

- `WaConnectButton.tsx` — FB SDK, `FB.login({config_id, response_type:'code'})`, слушатель
  `postMessage` до вызова login.
- `wa-onboarding.functions.ts` → `finishWaOnboarding`: обмен кода на токен, подписка на вебхуки,
  регистрация номера, создание 6 шаблонов, сохранение в `salon_secrets`.
- `wa-onboarding.server.ts` — весь разговор с Graph API, без базы. Разделение хорошее.

### 1.5 Интерфейс

`/admin/salons/$salonId` — 11 вкладок, 4000 строк в одном файле. Есть `OnboardingChecklist`
(4 шага: салон, услуги, мастера, сайт). WhatsApp живёт во вкладке «WhatsApp»: 4 карточки —
состояние, подключение, мост Make, шаблоны, диагностика.

## 2. Разрывы

Пронумерованы по критичности. Каждый проверен.

### БЛОКЕР-1. Self-service регистрации не существует

`/auth` в режиме `signup` создаёт пользователя и пытается выдать `super_admin` **только первому**.
Всем остальным роль не выдаётся вообще → `/admin` показывает «Нет доступа».

Создать салон тоже нельзя: единственная `INSERT`-политика на `salons` —
`has_role(auth.uid(),'super_admin')`. Владелец салона физически не может завести свой салон.

> Сегодня новый клиент не может пройти дальше первого экрана без ручного вмешательства
> оператора. Это, а не Embedded Signup, — главный блокер self-service.

Дополнительно: сам код выдачи первой роли (`user_roles.insert` из браузера) тоже упирается в
RLS `Super admin manages roles` и не может отработать.

### БЛОКЕР-2. Токен WhatsApp уезжает в браузер

`getWaCloudConfig` возвращает в клиент:

- `whatsapp_cloud_token` — постоянный токен с правами messaging + management над WABA салона;
- `whatsapp_cloud_app_secret` — секрет приложения (сейчас туда пишется **общий секрет платформы**,
  `finishWaOnboarding` кладёт `process.env.META_APP_SECRET` в строку каждого салона);
- `wa_make_token`.

`WaCloudCard` хранит их в React state и определяет `connected = phoneNumberId && token`.

Последствия: любой `salon_admin` (а также XSS, расширение браузера, чужой скриншот вкладки
DevTools) получает полный доступ к переписке салона; а через общий app secret — возможность
подделать подпись вебхука платформы для **любого** салона.

### БЛОКЕР-3. Embedded Signup v2/v3 отключается 15 октября 2026

Наш код передаёт `extras: { setup:{}, featureType:"whatsapp_business_app_onboarding",
sessionInfoVersion:"3" }`. Meta объявила hard deprecation v2 и v3 на **15.10.2026** — через пять
недель. Feature type для coexistence входит в список тех, что требуют ручной миграции и после
даты «свалятся в стандартный флоу», то есть coexistence сломается молча: номер уедет в Cloud API,
а WhatsApp Business на телефоне владелицы перестанет работать.

### БЛОКЕР-4. «Шаблоны готовы» поднимается раньше, чем Meta их одобрила

`createNotificationTemplates` считает шаг успешным по факту **создания**. Созданный шаблон
находится в статусе `PENDING`, а не `APPROVED`. `finishWaOnboarding` при этом сразу ставит
`salons.wa_cloud_templates_ready = true`.

Последствие: подтверждения и напоминания вне 24-часового окна уходят на шаблон, которого Meta ещё
не одобрила, и падают. Раньше это маскировалось откатом на Green-API — Green-API удалён, отката
больше нет. Статус шаблона нужно читать (`GET /{waba}/message_templates`) и/или принимать вебхуком
`message_template_status_update`, на который мы не подписаны.

### ВАЖНО-5. Нет жизненного цикла подключения

Состояние канала выводится из наличия двух полей. Нет различия между: не подключён / подключается /
подключён и здоров / токен отозван / WABA заблокирована / номер без платёжки / шаблоны на
модерации. Нет фонового health-check: об отозванном токене узнаём по тишине ассистента.

Не обрабатывается вебхук `account_update` (бан WABA, смена качества номера, потеря доступа) — Meta
его шлёт, мы игнорируем.

### ВАЖНО-6. Ассистент и WhatsApp-уведомления включает только super_admin

`salons.ai_assistant_enabled` и `salons.whatsapp_enabled` переключаются только под `isSuperAdmin`.
Вкладка «Ассистент» не показывается салону, пока флаг не поднят вручную. То есть даже с идеальным
Embedded Signup владелец не может включить то, ради чего пришёл.

### ВАЖНО-7. Устаревшие временные решения в интерфейсе владельца

- **Мост Make** — карточка с 4 блоками инструкций (регистрация на make.com, сборка сценария).
  В проде **ноль** салонов. После Advanced Access не нужен.
- **Ручной ввод реквизитов** — большой блок с App ID, WABA ID, токеном и системными пользователями,
  подписанный «Кнопка заработает после того, как Meta одобрит платформу». Текст стал ложным.
- **Gupshup** — карточка BSP, 1 тестовый салон. Нужна как запасной путь, но не владельцу салона.
- `salons.wa_provider` — все 7 салонов в проде стоят в `'green_api'`, транспорта которого больше
  нет. Колонка вводит в заблуждение.
- Дашборд `/admin` в «Быстром старте» до сих пор пишет «добавьте название, бренд, **GreenAPI
  ключи**».

### ВАЖНО-8. Разрывы изоляции тенантов в подключении

- Уникальность проверяется только по `phone_number_id` и только на пути кнопки. Ручное сохранение
  (`upsertWaCloudConfig`) её не проверяет — можно вписать чужой номер руками.
- На колонке нет уникального индекса в БД, только проверка в коде: две параллельные вкладки
  проходят её обе.
- `waba_id` не проверяется вовсе.

### ВАЖНО-9. Нет идемпотентности и ретраев

`finishWaOnboarding` — 9 последовательных вызовов Graph API без ретраев. Сеть моргнула на шаге 3 —
владелец видит ошибку, жмёт снова, код в это время уже сгорел (одноразовый, живёт минуты). Нет
журнала попыток: разобраться постфактум не по чему.

### СРЕДНЕ-10. Продукт и интерфейс

- Дашборд показывает 4 числа и не отвечает на вопрос «всё ли работает».
- Нет ни одного осмысленного empty state.
- Нет единой системы состояний (loading / empty / error) — каждая вкладка изобретает свою.
- Настройки салона — 11 вкладок в одном файле на 4000 строк, порядок вкладок случайный.
- Онбординг-чеклист не знает про WhatsApp и ассистента — то есть про главное.
- Технический язык в интерфейсе владельца: «Phone Number ID», «WABA», «app secret», «вебхук».

## 3. Реальные ограничения Meta после App Review

Проверено по документации Meta 09.09.2026. App Review **не снимает** следующее:

1. **Приложение должно быть переведено в Live.** Сейчас `Publish: Unpublished`. В development
   разрешения видны только разработчикам и тестировщикам приложения; чужой бизнес окно ES пройти
   не сможет.
2. **Лимит онбординга: 10 новых бизнес-клиентов в скользящие 7 дней.** Поднимается до 200 только
   после Business Verification + App Review + **Access Verification**. Это отдельная проверка,
   её ещё нет.
3. **Салон обязан привязать способ оплаты к своей WABA.** Мы — Tech Provider, а не Solution
   Partner: своей кредитной линией мы клиента не покрываем. Пока платёжки нет, сообщения не
   отправляются. Это обязательный шаг онбординга, который нужно показать в интерфейсе.
4. **Тарификация с 01.10.2026** — по сообщениям, а не по диалогам. Для KG ≈ $0.0077 за
   сообщение сервиса. Платит салон.
5. **Messaging tier.** Новый номер стартует с 250 уникальных получателей в 24 часа (1000 при
   верифицированном бизнесе), растёт по качеству. Ассистент отвечает внутри окна и в лимит
   почти не упирается, но напоминания — упираются.
6. **Coexistence:** пропускная способность фиксируется на 20 сообщений/сек; в приложении на
   телефоне перестают работать группы, исчезающие сообщения, трансляции, звонки, каталог/статусы.
   Требуется WhatsApp Business app ≥ 2.24.17.
7. **Rate limits Graph API** — 200–5000 запросов в час в зависимости от статуса аккаунта;
   не чаще одного сообщения в 6 секунд одному получателю.
8. **ES v2/v3 отключаются 15.10.2026** (см. БЛОКЕР-3).

## 4. План

### Фаза 0 — безопасность и корректность (блокеры публичного запуска)

0.1 Убрать секреты из ответа `getWaCloudConfig`; `connected` считать на сервере.
0.2 Реальный статус шаблонов: чтение статусов из Graph + вебхук `message_template_status_update`.
0.3 Миграция Embedded Signup на v4.
0.4 Уникальные индексы на `whatsapp_cloud_phone_number_id` и `whatsapp_cloud_waba_id`;
проверка чужой привязки на всех путях записи.
0.5 Обработка `account_update`: бан WABA, качество номера, отзыв доступа.

### Фаза 1 — self-service тенантность

1.1 RPC `create_salon_for_owner` (SECURITY DEFINER): заводит салон, филиал, роль `salon_admin`,
рабочие часы по умолчанию — одной транзакцией.
1.2 Регистрация без super_admin: новый пользователь → мастер онбординга.
1.3 Снять super-admin-гейт с `ai_assistant_enabled` и `whatsapp_enabled`.
1.4 Роут `/onboarding` — пошаговый мастер.

### Фаза 2 — жизненный цикл подключения

2.1 Модель состояний канала в БД + одна серверная функция, которая её считает.
2.2 Фоновая проверка здоровья подключения (cron) → состояние + уведомление владельцу.
2.3 Идемпотентность и ретраи Graph-вызовов, журнал `wa_onboarding_events`.
2.4 Переподключение, не ломающее данные.

### Фаза 3 — снос временного

3.1 Мост Make — из интерфейса владельца убрать (0 салонов), код и колонки оставить до сноса
отдельным шагом.
3.2 Gupshup — под super_admin.
3.3 Ручной ввод — под super_admin, текст переписать.
3.4 `wa_provider` — привести к реальности.

### Фаза 4 — продукт и интерфейс

4.1 Дизайн-система: токены, состояния, статус-бейджи, empty states, анимации.
4.2 Дашборд: «всё ли работает» первым экраном.
4.3 Онбординг-чеклист → полный путь до первого сообщения.
4.4 Язык интерфейса: бизнес вместо API.

### Фаза 5 — сквозная проверка

Регистрация → салон → услуги → мастер → WhatsApp → ассистент → реальное сообщение.

### Найдено и закрыто сверх плана

- **Экрана приглашения сотрудников не существовало.** `rbac.functions.ts` был написан целиком
  (`inviteEmployee`, `listSalonEmployees`, `revokeEmployeeAccess`, `setStaffIsolation`), но UI к
  нему не было ни одного: владелец не мог дать доступ администратору на ресепшене иначе как
  письмом в поддержку. Добавлена вкладка «Команда».
- **`listSalonEmployees` выгружал ВСЕХ пользователей платформы** страницами по 1000 на каждое
  открытие вкладки. Стоимость росла с числом клиентов Qabyl, а не с размером салона. Заменено на
  точечные запросы по известным идентификаторам.
- **Счётчик мастеров на дашборде терял мастеров с `branch_id = NULL`** — тем же способом, каким
  в июле 2026 сломался виджет записи целиком.
- **Мёртвый интерфейс Green-API** в настройках ассистента (карточка вебхука, подсказки про
  Instance ID) — транспорта нет с 28.08, а экран о нём рассказывал.
- **Посадочная не давала зарегистрироваться:** главная кнопка вела в `/admin`, то есть в редирект
  на вход.
- **Четыре ошибки типов**, лежавшие в репозитории до сессии. Проект впервые проходит `tsc`
  начисто.

### Не сделано и почему

- **Миграции не применены к проду.** Так устроено правило проекта
  (`.claude/skills/new-migration`): выкладка в прод — решение человека. Всё в
  `docs/LAUNCH-CHECKLIST.md`, пункт 1.
- **Сквозная проверка с реальным сообщением не проведена.** Она упирается в применённую миграцию
  и в новый `config_id` из кабинета Meta. Сценарий записан в чеклисте, пункт 9.
- **Шифрование токенов в базе не введено.** `salon_secrets` доступна только service-role, у роли
  `authenticated` нет `SELECT`, и теперь токен не покидает сервер — то есть основной путь утечки
  закрыт. Шифрование через Vault остаётся отдельной задачей: оно требует менять каждое чтение
  реквизитов, включая edge-функции.
- **Instagram-канал не переписан** под ту же модель состояний. Он работает и своей вкладкой
  владельца не блокирует; повторить для него `computeWaStatus` — следующий очевидный шаг.

# Ротация ключей после переезда Токио → Франкфурт

Задача числится незакрытой с 2026-08-11. Ниже — точный порядок.

**Почему это не сделано автоматически.** Ротация целиком состоит из действий,
которые я выполнять не должен: ввод учётных данных в дашборды, смена настроек
аккаунта, деплой в прод. Плюс половина шагов необратима — неверный порядок
кладёт продакшн до тех пор, пока вы вручную не вернёте старое значение. Поэтому
здесь чеклист, а не скрипт.

## Что ротируем и почему

Во время переезда старый проект (`khykprcdojksqvuqyajd`, Токио) и новый
(`bfxexnpyfslfuelfkhzr`, Франкфурт) какое-то время жили одновременно, а ключи
ходили между машиной, дашбордами и логами. Считаем скомпрометированным всё, что
могло быть скопировано в этот период.

| Секрет | Где выпускается | Где потребляется | Критичность |
|---|---|---|---|
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase → Settings → API | Cloudflare Worker, edge-функции | **Максимальная** — обходит RLS полностью |
| Пароль БД | Supabase → Settings → Database | `DATABASE_URL`, внешние подключения | Максимальная |
| `SUPABASE_PUBLISHABLE_KEY` / `VITE_SUPABASE_PUBLISHABLE_KEY` | Supabase → Settings → API | браузер (публичный) | Низкая — он и так публичный, но при ротации service-role меняется вместе с ним |
| `CRON_SECRET` | vault, читается `internal_get_cron_secret()` | триггеры БД → `send-whatsapp`, `send-reminders` | Высокая — им авторизуются рассылки |
| `GEMINI_API_KEY` | Google AI Studio | Worker | Средняя — утечка = чужие расходы |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET` | BotFather | ops-агенты | Средняя |
| `VAPID_PRIVATE_KEY` | сгенерирован один раз | push-уведомления | Низкая, но при смене **все подписки на push слетают** — см. предупреждение ниже |

Green-API токены салонов (`salon_secrets.greenapi_*`) и секрет приложения
Instagram переезд не затрагивал — они не менялись и в ротацию не входят.

## Порядок

Важно: сначала добавляем новое значение везде, где оно читается, и только потом
отзываем старое. Обратный порядок = простой продакшна.

### 1. Подготовка (5 минут)

- [ ] Убедиться, что деплой с текущими ключами зелёный. Ротация на сломанном
      проде не даст понять, что именно вы уронили.
- [ ] Открыть логи Worker'а (`observability` включается скриптом
      `scripts/patch-wrangler.mjs` при сборке) — они понадобятся, чтобы увидеть
      401/403 сразу после переключения.
- [ ] Выписать текущие значения в менеджер паролей. Откат должен быть возможен.

### 2. Service role key + пароль БД

- [ ] Supabase → Settings → API → **Generate new service_role key**.
- [ ] Cloudflare → Workers → `qabyl` → Settings → Variables → обновить
      `SUPABASE_SERVICE_ROLE_KEY`.
- [ ] Supabase → Edge Functions → Secrets → обновить там же (edge-функции читают
      свою копию: `send-whatsapp`, `send-reminders`, `send-push`,
      `cleanup-wa-media`).
- [ ] Передеплоить Worker и все четыре edge-функции.
- [ ] Проверить: открыть админку, календарь должен грузиться; создать тестовую
      запись у салона с выключенным WhatsApp.
- [ ] Только теперь Supabase → **Revoke** старый ключ.
- [ ] Supabase → Settings → Database → сменить пароль; обновить `DATABASE_URL`
      везде, где он задан.

### 3. CRON_SECRET

Он лежит в vault и читается из БД функцией `internal_get_cron_secret()`, а
edge-функции сравнивают с ним заголовок `x-cron-secret`. То есть значение должно
совпасть в двух местах одновременно.

- [ ] Обновить секрет в vault (SQL Editor, `vault.update_secret`).
- [ ] Сразу же обновить `CRON_SECRET` в секретах edge-функций и передеплоить их.
- [ ] Проверить: создать тестовую запись у салона с включённым WhatsApp и
      убедиться, что подтверждение ушло. Если в логах `send-whatsapp` видно
      `unauthorized internal call` — значения разошлись.

Между этими двумя шагами рассылки не работают. Делать в нерабочее время салонов.

### 4. Gemini и Telegram

- [ ] Google AI Studio → новый ключ → `GEMINI_API_KEY` в Cloudflare → передеплой
      → проверить ответ ассистента в симуляторе → удалить старый ключ.
- [ ] BotFather → `/revoke` → новый `TELEGRAM_BOT_TOKEN` → обновить в Cloudflare
      → заново установить вебхук бота → проверить, что ops-агент отвечает.

### 5. VAPID — только осознанно

⚠️ Смена `VAPID_PRIVATE_KEY`/`VAPID_PUBLIC_KEY` **инвалидирует все существующие
push-подписки**: каждому админу и мастеру придётся заново разрешить уведомления,
иначе они молча перестанут приходить. Ключи не участвовали в переезде и утечь не
могли. **Рекомендация: не трогать.** Если всё же меняете — предупредите салоны
заранее и почистите таблицу подписок, чтобы не копить мёртвые эндпоинты.

### 6. Закрыть старый проект

- [ ] Убедиться, что в Токио (`khykprcdojksqvuqyajd`) действительно пусто:
      `select count(*) from appointments;` должен вернуть 0.
- [ ] Скачать финальный дамп и положить в холодное хранилище.
- [ ] Удалить проект. Пока он жив, его ключи — это лишняя поверхность атаки, а
      его ключи ротацию не проходили.

## После ротации

- [ ] Прогнать `supabase/tests/schema_invariants.sql` — он не про ключи, но
      мгновенно скажет, жива ли база и не поехали ли права.
- [ ] Сутки последить за логами Worker'а на 401/403.
- [ ] Проверить, что напоминание за 2 часа ушло хотя бы по одной живой записи:
      это единственный путь, который проверяет связку vault ↔ edge-функция в бою.

# План тестирования Qabyl

Составлен 2026-08-13. Покрывает четыре зоны, которые ломают деньги и репутацию:
запись клиентов, расписание мастеров, предоплата, WhatsApp/Instagram.

## 1. Модель угроз: где на самом деле живёт логика

Ключевой факт, из которого следует весь план: **основная бизнес-логика Qabyl живёт
в Postgres, а не в TypeScript.** `create_appointment`, `reschedule_appointment_v2`,
`get_available_slots`, `confirm_prepayment`, `prepayment_expire_holds` — это
`SECURITY DEFINER` функции, вызываемые напрямую из браузера через PostgREST.

Отсюда два следствия для тестов:

1. Тестировать React-компоненты почти бесполезно — они не являются рубежом защиты.
   Клиент может вызвать RPC напрямую, минуя UI.
2. **Каждое правило, которое нельзя обойти, должно быть проверено на уровне SQL.**
   Поэтому основной набор тестов — SQL (`supabase/tests/booking_integrity.sql`),
   а не bun/jsdom.

Второй ключевой факт: **anon-роль имеет прямые табличные права на `appointments`**
(INSERT через RLS-политику `Anyone creates appointment`). Значит любой тест «через
UI прошло корректно» ничего не доказывает — нужно проверять, что и прямой путь закрыт.

## 2. Уровни тестирования

| Уровень | Что проверяет | Где | Запуск |
|---|---|---|---|
| L1 — инварианты схемы | гранты, RLS-политики, constraints, наличие guard-ов | `supabase/tests/booking_integrity.sql`, секция A | на ветке/локально |
| L2 — поведение RPC | двойная запись, буфер, выходные, перерывы, предоплата | `supabase/tests/booking_integrity.sql`, секции B–E | на ветке/локально |
| L3 — чистые функции TS | телефоны, парсинг дат, токены вебхуков, конфиг движка | `booking-integrity.test.ts` | `bun test` |
| L4 — сценарии ИИ | диалоги WA/IG, инструменты, промпты | существующие `wa-agent-*.test.ts` (45 сценариев) | `bun test` |

L1/L2 **нельзя гонять на проде**: они пишут в `appointments`, а на INSERT висит
триггер `dispatch_whatsapp_confirmation`, который реально шлёт WhatsApp клиенту.
Файл содержит предохранитель, который отказывается работать на боевом проекте.

## 3. Что именно проверяем

### 3.1 Запись клиентов (booking)

- B1. Нельзя создать пересекающуюся запись у одного мастера (RPC).
- B2. Нельзя создать пересекающуюся запись **прямым INSERT** в обход RPC.
- B3. Буфер после услуги (`buffer_after_min`) реально блокирует соседний слот.
- B4. Активный холд предоплаты (`pending_payment`) занимает слот так же, как `confirmed`.
- B5. Нельзя записаться в прошлое.
- B6. Нельзя записать мастера на услугу, которую он не оказывает.
- B7. Нельзя записать мастера в чужой филиал.
- B8. Телефон: 10–15 цифр обязательны; `source='import'` — единственное исключение.
- B9. Публичная запись (`source='widget'`) вне рабочего графика мастера отклоняется;
      ручная запись администратора (`source='manual'`) — разрешается (walk-in).
- B10. Запись в выходной мастера (`master_day_overrides.kind='off'`) и в отпуск
      (`master_time_off`) отклоняется для публичных каналов.
- B11. `price_override` работает только для `price_type='range'` и только внутри диапазона.

### 3.2 Расписание мастеров

- S1. `get_available_slots` не выдаёт слоты в выходной мастера.
- S2. Не выдаёт слоты во время `master_time_off`.
- S3. Не выдаёт слоты во время перерыва (`kind='break'`).
- S4. Учитывает часы филиала (пересечение с графиком мастера).
- S5. Пустой массив часов филиала на день = филиал закрыт, слотов ноль.
- S6. **Согласованность**: любой слот, выданный `get_available_slots`, должен
      успешно записываться через `create_appointment`. Расхождение здесь = клиент
      выбирает время и получает ошибку.
- S7. TS-зеркало (`classifyDayForService` в `wa-agent-v4.server.ts`) даёт тот же
      вердикт, что и SQL. Два независимых движка расписания — постоянный источник расхождений.

### 3.3 Предоплата

- P1. `confirm_prepayment` недоступна anon/authenticated (только service_role).
- P2. `prepayment_expire_holds` недоступна anon/authenticated.
- P3. Сумма процентной предоплаты считается от согласованной цены, не от нижней границы.
- P4. min/max клампы применяются.
- P5. Истёкший холд освобождает слот и переводит запись в `payment_expired`.
- P6. Оплаченный холд нельзя «потерять»: если поверх холда влезла чужая запись,
      `confirm_prepayment` не должна падать молча.
- P7. QR-путь вне префикса салона не сохраняется.

### 3.4 WhatsApp / Instagram

- W1. Вебхук без токена / с чужим токеном → 403.
- W2. Сравнение токена постоянное по времени (`safeStringEquals`).
- W3. Салон без `greenapi_webhook_token` не принимает вебхуки вообще.
- W4. Проверка номера в WA (`checkPhoneWhatsapp`) не блокирует запись при недоступности
      Green-API (fail-open) — и **это осознанное решение, а не баг**; тест фиксирует политику.
- W5. Пороги длины телефона согласованы между UI, wa-check и триггером БД.
- W6. `dispatch_whatsapp_confirmation` не шлёт сообщение для `source in ('ai_assistant','import')`.
- W7. Движок по умолчанию — v4; v3 только явным опт-ином.
- W8. Инъекция в имени отправителя WhatsApp вырезается.

## 4. Приоритет

1. **Сначала L1** — инварианты схемы. Они ловят самые дорогие баги (обход оплаты,
   спам-рассылка) за секунды и не требуют фикстур.
2. Затем L2 — поведение RPC.
3. L3/L4 уже частично есть; дополняем парити-тестами телефонов и вебхука.

## 5. Чего этот план сознательно НЕ покрывает

- Вёрстка и адаптив — визуальная регрессия отдельная тема, дешевле смотреть глазами.
- Реальные вызовы Gemini — недетерминированы; сценарные тесты мокают модель.
- Нагрузочное тестирование — актуально после 4 салонов, не раньше.

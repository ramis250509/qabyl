# Новая миграция

В `supabase/migrations/` уже 115 файлов, и схема — это то, на чём стоит вся запись
клиентов. Правила ниже выведены из реальных поломок, а не из общих соображений.

## Имя файла

`supabase/migrations/YYYYMMDDHHMMSS_краткое_имя_латиницей.sql`

Метку времени бери текущую (UTC) и **проверь, что такой префикс ещё не занят**:

```bash
ls supabase/migrations | tail -5
```

В репозитории уже есть коллизия — два разных файла с префиксом `20260812120000`. Порядок
применения при совпадении меток не определён, поэтому новых дублей не создавай.

## Обязательные правила

1. **Идемпотентность.** `create table if not exists`, `add column if not exists`,
   `drop constraint if exists` перед `add constraint`. Миграцию могут прогнать повторно.

2. **Значения enum — отдельным файлом.** Postgres не даёт использовать только что
   добавленное значение перечисления в той же транзакции (SQLSTATE 55P04), а файл
   миграции выполняется одной транзакцией. Именно на этом цепочка однажды перестала
   разворачиваться с нуля — см. `20260801125900_appointment_status_enum_values.sql`.
   Добавляешь значение и сразу хочешь на него индекс или проверку — это два файла.

3. **RLS для каждой новой таблицы.** База общая на все салоны:

   ```sql
   alter table public.новая_таблица enable row level security;
   ```

   Политика обязана ограничивать по салону. `using (true)` в этом проекте —
   не политика, а дыра.

4. **Значения по умолчанию сохраняют текущее поведение.** Новая колонка-переключатель
   получает default, равный тому, как система работает сейчас. После наката не должно
   измениться ничего, пока переключатель не тронут руками. Эталон —
   `20260815130000_whatsapp_cloud_api.sql`: `wa_provider` по умолчанию `green_api`.

5. **Комментарий сверху — зачем, а не что.** SQL и так виден. Ценно то, какая проблема
   лечится и как её обнаружили. Посмотри соседние файлы, там это выдержано.

## После создания файла

Скажи явно, что миграция **создана, но не применена**, и предложи применить отдельным
шагом. Сам не применяй: выкладка в прод — решение человека.

## Как применять, чтобы не расходились номера

`apply_migration` в Supabase MCP **не принимает номер версии** — только имя и SQL, а
номер присваивает сам, по времени применения. Поэтому:

**Передавай в `name` РОВНО ту часть имени файла, что идёт после метки времени.**
Файл `20260817074819_followups.sql` → `name: "followups"`. Без `.sql`, без номера,
буква в букву.

Имя — единственное, что связывает файл в репозитории с записью в базе. Совпадает имя —
`scripts/check-migrations.mjs` сопоставит их и скажет «применена под другим номером,
это норма». Не совпадает — миграция будет числиться непринятой, а в базе появится
запись-призрак без файла. Именно так 19.08.2026 пять миграций «потерялись».

Номера при этом разойдутся, и это нормально: переименовывать файл под номер из базы
не нужно.

После применения прогоняй сверщик — он подтвердит, что связь не порвалась:

```bash
node scripts/check-migrations.mjs < db-migrations.json
```
